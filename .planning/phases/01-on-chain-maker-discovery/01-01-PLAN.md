<objective>
The tracer slice: one maker registers on a real, deployed `rfq_registry` on Testnet and is
discovered and refunded, end to end, through every layer this phase touches.

Purpose: this phase's whole architecture rests on three assumptions the repo has never exercised —
that a plain `initialize` with an explicit re-init guard works where `rfq_swap` used a
`__constructor` (RESEARCH.md Pitfall 1), that the contract can hold and *refund* native XLM as the
`from` of its own SAC transfer with no extra auth step (RESEARCH.md Assumption A1), and that a new
Cargo workspace member does not move `otc_swap`'s deployed wasm hash. Proving all three on one thin
path, before ten more entry points are written on top, is worth more than a complete contract that
turns out to be built on a wrong assumption.

Output: the `rfq_registry` crate wired into the workspace with `initialize` / `set_url` /
`get_maker` / `eject` / `get_config` only, a minimal unit-test module, a live deployment on
Testnet, and `tools/rfq-registry-live.mjs` proving the round trip with exact balance deltas.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| any Stellar account → `rfq_registry` entry points | Fully permissionless; any funded account can call `set_url`/`eject` with arbitrary arguments |
| `rfq_registry` → native XLM SAC | The contract is the escrow; staked value sits in its own SAC balance |
| deployer identity → `initialize` | The one-shot admin-establishing call; whoever wins the race owns the instance |
| maker-supplied `url` string → future desk fetch (Phase 2) | Attacker-controlled data stored on a public ledger and later read by a browser client |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
