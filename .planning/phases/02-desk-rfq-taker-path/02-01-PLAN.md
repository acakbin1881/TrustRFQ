<assumption_delta_decision>
**Noun:** settlement lane.

**Situation:** this phase introduces a SECOND settlement path into the desk. The existing lane is
identified by a Supabase `orders` row and driven by `src/ui/useSettlement.ts`; the RFQ lane
deliberately has NO persistence at all (D-03). That is a pluralization seam: the question is
whether "an order row" is still the right primary noun for "a thing the desk settles".

**Decision: add-alongside.** A separate `RfqPanel`, a separate settlement module
(`src/core/rfq/settle.ts`) and a separate panel-local busy guard. The OTC lane is not touched, not
generalized, and not renamed. This is what 02-CONTEXT.md already locks (D-01 separate panel, D-03
no persistence) and what 02-RESEARCH.md's anti-pattern list requires (the OTC settlement hook is
scoped to the `maker_auth`/`taker_auth` columns and its own serialization lock; routing RFQ
through it is explicitly forbidden).

**Accepted debt:** two settlement code paths with different persistence models and two independent
busy guards, so "is a settle in flight?" has no single answer across the desk. Acceptable because
the two lanes cannot interleave for one user action and neither reads the other's state.

**What would force a later promote:** the decided-but-unbuilt `otc_swap` -> `rfq_swap` contract
merge recorded in CLAUDE.md's Status section (2026-08-19: one contract settles both lanes,
`Order` gains `require_fill_guard`, new wasm and contract id). When that lands, both lanes settle
through one contract and the two settlement modules should collapse into one with persistence as
an injected concern. Nothing in this phase should make that collapse harder: keep
`src/core/rfq/*` free of UI and storage concerns.
</assumption_delta_decision>
